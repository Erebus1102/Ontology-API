# TKOS Ontology V2.3 辩护与修订说明

## 本轮结论

审计提出的三项问题均成立，已全部修订。V2.3 聚焦机器可执行性：修复 SPARQL 语法、使每个负向样例具备独立的共同基线，并补足责任承担周期的四种边界失败情形。

## 逐项裁定

### 1. RoleAssignmentShape 的 SPARQL UNION 无法解析

**裁定：成立，已修订。**

原查询把 `FILTER NOT EXISTS` 左侧直接连接到 `UNION`，不构成两个完整的分组图模式；终点分支也没有自行绑定 `?interval`。这不符合 SPARQL 1.1 的 GroupGraphPattern 语法，无法作为可发布的 SHACL 约束。

V2.3 将该规则拆成两条独立约束：

- 起点约束绑定当前 `RoleAssignment` 的 `hasValidityInterval` 与 `validFrom`，要求 `time:hasBeginning/time:inXSDDateTime` 等于 `validFrom`。
- 终点约束绑定当前 `RoleAssignment` 的 `hasValidityInterval` 与 `validUntil`，要求 `time:hasEnd/time:inXSDDateTime` 等于 `validUntil`。

每条失败结果可直接定位到起点或终点。

### 2. 周期规则缺少四类负向夹具

**裁定：成立，已修订。**

新增 `tests/v2.3-role-assignment-cases.trig`，每个 case 只保留一个故意错误：

- `test-negative-early-end`：有限 Mission 的承担提前结束。
- `test-negative-open-mission-finite-assignment`：开放 Mission 使用有限承担。
- `test-negative-interval-start`：`validFrom` 与区间起点不一致。
- `test-negative-interval-end`：`validUntil` 与区间终点不一致。

同时保留 `test-negative-role` 作为 DRI 角色、范围和起点未覆盖的控制组。每个负向 case 的预期均为恰好一条违规；夹具避免将两个错误混在同一个实例中。

### 3. 负向图依赖正向图基线

**裁定：成立，已修订。**

V2.1 的 `test-negative` 借用了 `test-positive` 中的人员、来源、结果和上下文资产。单独加载时，这些引用不封闭，干扰了责任规则本身的验证。

V2.3 抽出显式的 `test-baseline` 命名图，容纳共同且完整的 Person、Role、Domain、SourceRecord、Outcome、Evidence、Review、Rationale 及其 ConfirmationEvent。`run_v2_3_shacl.py` 明确将基线与单一 case 合并为数据图后运行，任何 case 都不依赖另一个 case。这样的装配表达了测试前提，也避免了跨图隐式依赖。

## 实测结果

使用 pySHACL 0.40.1、RDFS 推理与 advanced SHACL：

| 用例 | 预期 | 实测 |
| --- | --- | --- |
| `test-positive` | 通过，0 条违规 | 通过，0 条违规 |
| `test-negative-role` | 失败，1 条违规 | 失败，1 条违规 |
| `test-negative-early-end` | 失败，1 条违规 | 失败，1 条违规 |
| `test-negative-open-mission-finite-assignment` | 失败，1 条违规 | 失败，1 条违规 |
| `test-negative-interval-start` | 失败，1 条违规 | 失败，1 条违规 |
| `test-negative-interval-end` | 失败，1 条违规 | 失败，1 条违规 |

本体 JSON-LD、SHACL JSON-LD 与 V2.3 TriG 夹具均可由 rdflib 解析；SHACL 中 8 条 SPARQL 查询均完成语法解析。

## SWRL 验证补充

Openllet 已完成四个 `MissionReadyForAcceptance` 蕴涵场景的实测：

| 场景 | 实测蕴涵 |
| --- | --- |
| 完整 Evidence、Review、Confirmation | 是 |
| 缺 Evidence | 否 |
| 缺 Review | 否 |
| 缺 Confirmation | 否 |

执行器同时读取原始 JSON-LD，确认 `Rule_MissionReadyForAcceptance` 保持 8 个 body 原子、1 个 head 原子，且 head 指向 `MissionReadyForAcceptance`。Openllet CLI 不支持直接读取 JSON-LD；通用 RDF/XML 序列化会因其 SWRL `body/head` 读取顺序而失真。因此测试执行器使用规范 RDF/XML 适配层，并要求 `swrl:head` 出现在 `swrl:body` 前。这一适配层属于推理运行时工件，不改变 V2.3 本体的 RDF 语义。

## 边界与下一步

V2.3 已关闭 SHACL 与验收规则的推导验证。进入真实实例试点前，仍需将规范 RDF/XML 适配器纳入发布管线，并以真实 Mission、Evidence、Review、Confirmation 数据跑一轮来源、权限和时间范围过滤后的 Context Pack 验证。

## Context Pack 运行时演示验证

已新增脱敏的五图测试场景与 Context Resolver。`mission_review` 只读取已确认企业事实图和决策溯源图，得到 Mission、业务域、目标、当前 Evidence、Review、Rationale、Learning 与来源记录；它排除过期 Evidence、候选 Evidence 和敏感个人断言。`persona_replay_authorized` 在显式允许敏感个人记录后，才增加该断言。

两个物化出的 `ContextPack` 均带有对象标识、用途显示名、运行时来源、有效时间、使用时间、确认状态和 `hasContextMember` 成员关系。以 V2.3 SHACL 形状复核，物化 ContextPack 通过 `ContextAssetShape` 与 `SourceRecordShape`。

这证明了筛选与可追溯链路，使用的名称和内容均为测试数据。真实试点仍需由业务方提供一项实际或脱敏导出的 Mission，并确认该 Mission 的用途、可读取图、时间点及敏感信息处理规则。

```text
FE Domain
  └─ Domain Outcome
       FE 支撑两条真实战略决策闭环
       ├─ FE-M1 词元云集内部真实战略决策闭环
```

| FE-M2 | 用可迁移 Context 支撑灯塔项目的一条真实战略决策闭环 | 需要客户议题、授权、材料、王总使用与验证计划；房懂懂 Agent 架构仍待真实任务验证 |
| FE-M3 | 将两条闭环沉淀为最小可复用 FE 能力 | 以 M1、M2 的真实消费决定能力边界；CO Agent、Ontology、TokenHub 尚缺可核验产物与联调记录 |

## 当前候选决策

**采用 CEO Agent 优先的词元云集与房懂懂双场景验证路径**处于 `DecisionPendingConfirmation`。

它已连接产品 1.0 与灯塔交付议题、两条场景议题、Week 1 验证方案研究、房懂懂推理 Agent 执行计划、房懂懂决策系统价值模型，以及 CEO Agent 产物反馈。它等待 CEO 的确认事件后才可作为生效决策使用。

以下情况触发复审：本周 MVP 未产出；任一场景无法锁定真实事项、材料或参与者；王总无法开始使用；双场景反馈显示方法、产品或 FE Context 无法支撑战略决策闭环。

## 两个业务验证场景

### 场景一 词元云集工作方法建设

当前以“本季度能否同时完成产品 1.0 上线和灯塔项目交付”为真实经营议题。Agent 应接收已确认的 FE Mission Card 结构、灯塔计划、Week 1 会议纪要、产品 1.0 更新和 CEO Agent 反馈。

一次合格运行应形成以下产物：

1. 议题、相关 Outcome、Mission、DRI、依赖、风险与缺口的结构化 Context Pack。
2. 可选路径和每条路径的依据、条件、代价与待确认事实。
3. 清晰区分事实、来源明确的主张、候选判断与未知项。
4. 供会议使用的 Decision 草案和 Review 条件。

人工核验关注四件事：关键事实能否追到来源；当前未知是否被明确指出；是否把候选写成已确认结论；输出能否帮助决策者推进一次实际取舍。

### 场景二 房懂懂业务本体设计选择

当前材料给出了房产买卖、置换与时机判断的决策支持方向，数据与估值、业务本体与规则、好时机 Agent 迭代的并行建设方式，以及统一评测框架。业务本体设计的具体备选方案与授权确认尚未提供。

一次合格运行应形成以下产物：

1. 房懂懂的候选业务对象、关系、决策问题和 Context 边界。
2. 每个候选对象对应的来源片段、适用范围与待确认项。
3. 至少一个真实房产决策任务的评测输入，覆盖业务效果、任务能力、工程能力、多 Agent 能力、安全与治理。
4. 架构或本体设计选择的比较表，以及进入确认前仍需补齐的证据。

## 当前最重要的缺口与风险

| 类别 | 内容 | 对运行的影响 |
|---|---|---|
| Context 缺口 | CEO Agent 对公司已有内容、当前现实与本体关系的理解不足 | 容易给出结构完整但贴合度不足的产物 |
| 使用缺口 | 王总尚未开始使用 CEO Agent | 灯塔“常态化高质量使用”缺少真实用户证据 |
| 产品缺口 | CO Agent、Ontology、TokenHub 尚无可蒸馏产出、入口或运行记录 | 无法验证产品 1.0 的联合上线与闭环运行 |
| 架构风险 | 房懂懂 Agent 架构尚未以真实决策任务对照验证 | 技术选择缺少业务任务证据 |
| 资源风险 | 产品 1.0 上线与灯塔交付在三周窗口内存在跨 Domain 资源冲突 | 需要公司级 Mission Portfolio 做取舍 |

## 从业务验证回写本体

```text
真实议题与材料
  → Context Resolver 生成场景 Context Pack
  → CEO Agent 产出候选判断、方案和待确认项
  → DRI 核验事实，会议确认 Decision
  → 写入 Evidence、MissionReview、ConfirmationEvent
  → Openllet 推导 MissionReadyForAcceptance
  → 形成下一周期可复用的 Context 与学习
```

业务验证的完成标志是一次真实事项已经形成可追溯的 Decision，并拥有对应的 Evidence、Review 与 ConfirmationEvent。届时才能把相关 Mission 送入验收推导；当前实例图还处于将运行事实、授权与使用证据逐项补齐的阶段。
